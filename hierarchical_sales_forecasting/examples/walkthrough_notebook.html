Multi-Metric Cascading & Reconciliation — Walkthrough

End-to-end notebook: how an analyst takes one CSV of historical performance + pipeline data and produces a quota plan, a pipeline diagnosis, a redistributed plan, and a bias-corrected forecast — with full visibility into how each metric actually influences allocation.

Package: b2b-revenue-forecasting Version: 0.25.0 Dataset: 170 ICs · 217 hierarchy nodes Macro target: $50,000,000

Quickstart

From the project root, run both scripts:

pip install -e .

python examples/walkthrough.py

2Build the hierarchy (with the brand-new flag)#

A single SalesHierarchy.from_dataframe(...) call constructs the DAG, attaches every metric column to the IC nodes, and ingests the Is_Brand_New CSV column into a special attribute _is_brand_new the cascader can find later.

Code

from b2b_revenue_forecasting import SalesHierarchy

taxonomy = ['Global', 'Region', 'RVP', 'Director', 'Manager', 'IC']
metrics_cols = [
    'Q1_NetNewACV','Q2_NetNewACV','Q3_NetNewACV','Q4_NetNewACV',
    'Q1_CloudSeats','Q2_CloudSeats','Q3_CloudSeats','Q4_CloudSeats',
    'Q1_DCSeats','Q2_DCSeats','Q3_DCSeats','Q4_DCSeats',
    'LTM_ExpansionSpent',
    'Q1_Has_Active_Cert','Q2_Has_Active_Cert',
    'Q3_Has_Active_Cert','Q4_Has_Active_Cert',
    'Open_Pipeline','Late_Stage_Commit','Best_Case_Adds',
]
hierarchy = SalesHierarchy()
hierarchy.from_dataframe(
    df, path_cols=taxonomy, metrics_cols=metrics_cols,
    brand_new_col='Is_Brand_New',   # ingest the flag from CSV
)

Output

Regions:  ['NA', 'EMEA', 'APAC']

Key idea. The brand-new IC list lives in the CSV, not in Python. Analysts mark new reps directly in their spreadsheet.
Data hygiene is automatic since v0.6.x. from_dataframe now heals or flags the classic dirty-CSV traps: a row repeating the same value at two levels is auto-renamed instead of creating a self-loop (on_collision='suffix', also 'skip'/'error'); blank or literal "nan" cells are treated as missing instead of collapsing branches; metric cells are coerced (numpy scalars, "true"/"false", "$1,200", "12.5%") with uncoercible values warned and dropped — never a silent 0; and the finished graph is DAG-validated, so a cycle raises HierarchyValidationError naming the path instead of a RecursionError at cascade time. hierarchy.validate() re-checks on demand. And since v0.19.1 the cascader also guards metric grain (issue #36): if a metric or gate is identical across nearly every leaf-sibling group — the signature of an ancestor-level value repeated onto leaf rows, which double-counts and equal-splits silently — it warns, naming the column. Metric columns must be at LEAF grain; resolve coarser grains in the feed query. And since v0.7.2 you rarely need the raw graph: roots(), leaves(root=None), managers(root=None), and node_depths() answer the common questions, while .graph is the one canonical accessor on every class (.hierarchy works too, as an alias).

3Declare which metrics drive cascading + their direction#

Direction is always a user input. The analyst declares whether more-of-X means more quota (proportional) or less quota (inverse). The package never overrides this from data.

Code

from b2b_revenue_forecasting import MetricSpec

declared_metrics = [
    MetricSpec('NetNewACV',       direction='proportional', weight=1.0, lookback=4),
    MetricSpec('CloudSeats',      direction='proportional', weight=1.0, lookback=4),
    MetricSpec('DCSeats',         direction='inverse',      weight=1.0, lookback=4),
    MetricSpec('ExpansionSpent',  direction='inverse',      weight=1.0,
               columns=['LTM_ExpansionSpent']),
    MetricSpec('Has_Active_Cert', direction='proportional', weight=1.0, lookback=4),
]

Output

CloudSeats         direction=proportional  lookback=4
DCSeats            direction=inverse       lookback=4
ExpansionSpent     direction=inverse       lookback=4  (single LTM column)

Note. Metric names are arbitrary strings. Has_Active_Cert is a boolean column — the cascader auto-detects 0/1 data and skips zero-imputation. Single-column metrics like LTM_ExpansionSpent use the explicit columns=[...] argument.

4Suggest weights for ALL secondary metrics#

All four secondary metrics (CloudSeats, DCSeats, ExpansionSpent, Has_Active_Cert) go through suggest_weights. NetNewACV is the cascade target itself — correlating it with itself is always 1.0 — so we pin it manually later as the anchor.

For boolean metrics, we aggregate per-quarter columns into a single per-IC count (0–4) so the correlation is meaningful:

Code

# Aggregate the 4 quarterly boolean cert columns into one per-IC sum
df['Has_Cert_4Q_sum'] = (
    df[['Q1_Has_Active_Cert', 'Q2_Has_Active_Cert',
        'Q3_Has_Active_Cert', 'Q4_Has_Active_Cert']]
    .astype(int).sum(axis=1)
)

candidates = [
    {'name': 'CloudSeats',      'column': 'CloudSeats_4Q_sum',
     'direction': 'proportional', 'lookback': 4},
    {'name': 'DCSeats',         'column': 'DCSeats_4Q_sum',
     'direction': 'inverse',      'lookback': 4},
    {'name': 'ExpansionSpent',  'column': 'LTM_ExpansionSpent',
     'columns': ['LTM_ExpansionSpent'],
     'direction': 'inverse',      'lookback': 1},
    {'name': 'Has_Active_Cert', 'column': 'Has_Cert_4Q_sum',
     'direction': 'proportional', 'lookback': 4},
]
suggested, report = MetricSpec.suggest_weights(
    df, target_column='NetNewACV_4Q_sum',
    candidate_metrics=candidates,
)

Output

Suggested weights:
  CloudSeats         direction=proportional  weight=0.980  corr=+0.980  (agrees)
  DCSeats            direction=inverse       weight=0.117  corr=-0.117  (agrees)
  ExpansionSpent     direction=inverse       weight=0.095  corr=-0.095  (agrees)
  Has_Active_Cert    direction=proportional  weight=0.624  corr=+0.624  (agrees)

No direction-mismatch warnings fired — data agrees with all directions.
What you got. CloudSeats at +0.98 is the strongest secondary signal. Has_Active_Cert at +0.62 is a meaningful proportional pull. DCSeats (0.117) and ExpansionSpent (0.095) came back weak but in the expected directions, so they carry small data-driven weights. If a metric's data sign ever disagrees with the analyst's declared direction, the package warns loudly — but keeps the user's call. Degenerate slices (single row, zero variance, all-null columns) never raise — and since v0.12.0 they no longer silently equal-split either: statistically-undefined candidates KEEP their declared weights by default (on_degenerate='proportional'), so a 2-team slice with a 6x seat difference splits ~6x, not 50/50. The report flags them (degenerate/fallback), a warning names them, and on_degenerate='equal' (weight 0 → equal split, with the v0.10.2 warning) or 'raise' restore stricter behaviors.
Suggested specs are directly usable (v0.7.1). How a spec finds its data, in order: explicit columns=[...] always wins → the Q1_<name>…Q<lookback>_<name> convention (what this walkthrough's quarterly columns use) → new: the plain column named exactly <name>. So if your data has one flat column per metric (knowledge_workers, dc_seats), specs from suggest_weights just work — the old for s in suggested: s.columns = [s.name] boilerplate is obsolete. The column= field above is used only for the correlation math and is never copied into the spec. And if an active metric resolves to zero signal across the whole tree (e.g., a typo'd name), cascade_quota now warns and lists the columns it tried.

5Override a suggested weight (Pattern A)#

The RevOps team believes DCSeats is a bigger headwind than the historical data alone reflects (maybe a known platform sunset). The analyst overrides just that weight — the rest stay data-driven.

Code

# Edit in place — suggested is a list of MetricSpec, fully mutable
for s in suggested:
    if s.name == 'DCSeats':
        before = s.weight
        s.weight = 0.4   # analyst's domain judgment
        print(f"  DCSeats weight: {before:.3f} (suggested) -> {s.weight:.3f}")

# Pin the cascade target (NetNewACV) at the anchor weight of 1.0
cascade_metrics = [
    MetricSpec('NetNewACV', direction='proportional', weight=1.0, lookback=4),
    *suggested,
]

Output

DCSeats weight: 0.117 (suggested) -> 0.400 (overridden)

Final cascade metric set:
  NetNewACV          direction=proportional  weight=1.000
  CloudSeats         direction=proportional  weight=0.980
  DCSeats            direction=inverse       weight=0.400
  ExpansionSpent     direction=inverse       weight=0.095
  Has_Active_Cert    direction=proportional  weight=0.624
Pattern B alternative. Instead of mutating, you can build the final list by hand: by_name = {s.name: s for s in suggested}; cascade_metrics = [MetricSpec('NetNewACV', ...), by_name['CloudSeats'], MetricSpec('DCSeats', ..., weight=0.4), by_name['Has_Active_Cert']]. Either pattern works — mix-and-match between data-driven and hand-picked weights freely.

The actual cascade. The metrics blend at every level. Per-region hedges: NA aggressive 10%, EMEA + APAC standard 5%. Brand-new ICs flagged in the CSV are picked up automatically. The normalized-weights table auto-prints at the top of every cascade.

What happened mathematically. At every parent node, each child's share = weighted sum of (per-metric share-of-siblings), with weights normalized to 1. Inverse metrics flip via reciprocal-then-normalize. The 29 brand-new ICs each got equal-share carve-out before veterans split the remainder.
New in v0.5.0 — the base layer comes free. Every cascade_quota call now also computes the un-hedged cascade internally and stores it on cascader.base_quotas. The base layer is the reconciliation currency: it sums to the macro target at every depth, while the hedged layer legitimately compounds overassignment down the tree. Snapshot it right after the cascade you care about — a later cascade call (like the CRO-override re-run in Step 9) overwrites it.

9Re-cascade with a CRO override for a strategic hire#

The CRO decides one IC must carry exactly $1.2M. The cascader carves that out first and lets the algorithm distribute the remainder among siblings.

Code

# hedge factor instead.
quotas_with_override = cascader.cascade_quota(

Output

[Normalized-weights table reprints — see Step 8]

IC_Mgr_Dir_RVP_NA_2_2_1_3 algorithmic quota:   $  340,167.63
IC_Mgr_Dir_RVP_NA_2_2_1_3 CRO-locked quota:    $1,200,000.00

How it interacts. Override is carved out first; remainder within the manager's team is split by the multi-metric algorithm (renormalized among the unpinned, so the parent total is conserved exactly). Brand-new IC carve-outs never stack on top of overrides. Since v0.18.1 the absorption policy is stated and regression-pinned (issue #37): the remainder flows to non-pinned siblings proportional to their baseline (un-pinned) cascade — an algebraic identity of renormalized shares, verified to the penny.
Pins grew up in v0.13.0 (issues #28/#21/#23). Pins now work at any level — pin a manager and that subtree's total is fixed, then cascades normally within; jagged-hierarchy leaf pins are honored too (both were silently ignored before). Conservation is guaranteed: the brand-new carve-out is capped at the remaining pool, and a pin exceeding the pool floors siblings at $0 — never negative quotas — with a warning plus overpinned_amount/overpinned_nodes in gating_report(). Pins carry a basis: override_basis='base' (default — pin the un-hedged plan number; hedged derived) or 'cascaded' (shown above — pin the exact final number; base derived). And for post-cascade edits, work on base_quota, roll parents up on base, then cascader.rehedge(edited_base) re-derives the hedged layer from each node's original ratio (cascader.hedge_ratios()) — summing hedged leaves into parents double-counts buffers up the tree.

13Export all outputs to CSV (with hedge audit)#

Since v0.5.0 there's no second cascade: the un-hedged baseline was captured from cascader.base_quotas back in Step 8. The CSV gets both columns plus the dollar buffer and overassignment percentage per node, giving stakeholders a clean audit trail of where the hedging dollars went. (If the quotas dict you're exporting came from the most recent cascade call, you can skip the snapshot entirely and pass unhedged_quotas='auto'.)

Code

import os

16Part B — White-space cascade with a hard gate#

The alternative planning philosophy: instead of historical attainment, cascade on FORWARD-looking signals — current installed seats (where can they expand?), knowledge-worker counts (how big is the addressable account?), LTM spend (dampener — high recent spend leaves less headroom). Then apply a hard gate: territories with zero unmigrated seats get $0 because there's no white space to sell into, full stop.

When to use this. White-space planning is right when past attainment is noisy (rapid growth, territory shuffles, recent re-orgs) and the org wants every rep measured against the opportunity actually in front of them. It's an explicit fairness choice: "what can be achieved" trumps "what has been done."

Code

# Forward-looking metric slate (no historical attainment here)

    MetricSpec('Current_Seats_ProductX',  direction='proportional',
               weight=1.0, columns=['Current_Seats_ProductX']),
    MetricSpec('Knowledge_Workers_Count', direction='proportional',

How gates work mathematically. Before the weighted blend runs at each level, the cascader checks every child against every gate. Gated children get quota = 0 and are removed from the blend pool — the non-gated siblings absorb the full target_to_distribute via the existing share-of-siblings math. Because gate values aggregate from leaves upward, a non-leaf is automatically gated iff all its descendants fail the gate. No extra propagation logic needed. Multiple gates compose with AND. CRO overrides win over gates.
Configurable gate semantics (v0.9.0). The PASS predicate is now a knob: gate_mode='gt' (default — pass iff value > gate_threshold, exactly the behavior above), 'ge' ("at least N seats": gate_threshold=5, gate_mode='ge' lets a rep with exactly 5 pass), 'lt'/'le' (gate reps with too much of a signal — e.g. gate_threshold=100, gate_mode='le' zeroes churn-heavy territories), and 'truthy' (boolean entitlement flags, threshold ignored). Every mode inherits the gate_fallback no-stranding guarantees.
The is_gated column matters for audit. It distinguishes "$0 because gated" (a deliberate exclusion the planner chose) from "$0 because the metric signals were weak" (algorithmic outcome). Stakeholders should see this distinction.
Deterministic proportional splits (v0.17.0, issue #34). The most common allocation — "this team holds 30% of the seats → 30% of the quota" — never needed correlation or suggest_weights: fixed-weight MetricSpecs have always been used as-is. It now has a named front door:

17Gate fallback + per-depth reconciliation — v0.5.0, issue #12#

The bug this fixes: pre-v0.5.0, if every leaf under the cascade root failed the gate (e.g., a Migration cascade where no rep in the whole slice had DC entitlement), the root was gated to $0 and the target silently vanished. Consumers who patched depth 0 back to the target got a depth-1 shortfall equal to the fully-gated slice's target. Now: the root is never gated to $0, and the base (un-hedged) layer sums to the target at every depth.

The gate_fallback preference order. A fully-gated subtree's share first flows to its nearest non-gated siblings — that's the normal gate rollup, unchanged (a fully-gated team's quota goes to its sibling teams within the same sub-region, keeping the sub-region split consistent). Only when EVERY child of a funded node is gated does the fallback kick in: 'redistribute' (default) relaxes the gate at that level as a last resort so the target still reaches ICs; 'strand_at_root' keeps the money visible on the deepest non-gated ancestor and reports it via cascader.unallocated; 'error' raises GateAllocationError.

Code

# (a) Per-depth reconciliation of the Step-8 base layer — the invariant

    quotas_unhedged, target=50_000_000.0, strict=True,
)

# (b) The issue-#12 scenario: cascade into a slice whose leaves are ALL
#     gated (Mgr_Dir_RVP_APAC_1_1_1 — zero unmigrated seats anywhere).
slice_quotas = cascader_ws.cascade_quota(
    'Mgr_Dir_RVP_APAC_1_1_1', 1_000_000.0,
    metrics=forward_metrics,
    gate_metrics=gate_metrics,      # gate_fallback='redistribute' is default
)

# (c) The explicit opt-out — keep the money visible instead:
strand_quotas = cascader_ws.cascade_quota(
    'Mgr_Dir_RVP_APAC_1_1_1', 1_000_000.0,
    metrics=forward_metrics,
    gate_metrics=gate_metrics,
    gate_fallback='strand_at_root',
)

# gate_fallback='error' would raise GateAllocationError instead

With group_keys like ["st1_sales_type", "base_product_r4f", "regional"] the same call scales to hundreds of combinations — replacing the ~150-line bespoke loop from issue #4. Since v0.15.0, gate_metrics may also be a callable evaluated per combination (lambda g: DC_GATE if g['st1_sales_type'] == 'Migration' else None) — conditional gating in one call instead of a split-and-concat pair, exactly equivalent number-for-number (pinned by test). Aggregate pins across cascades (v0.16.0). "This territory carries exactly $500k in TOTAL across every product and quarter" is one call on the batch output: apply_pins(quotas_long, pins=[Pin(node, 500_000)], freeze_nodes=[...]). The pinned node keeps its baseline mix across combos; siblings absorb each cascade's delta proportionally (manager pins and manager absorbers rescale whole subtrees, parents conserve, floors at $0 — never negative); frozen/excluded nodes are never touched (issue #24) — and since v0.20.0 (issue #39) that protection reaches inside subtrees: a manager pin rescales AROUND descendants that are separately pinned, frozen, or excluded (free siblings stretch to fill, so pin order no longer matters), absorption is weighted by free capacity, and a basis='cascaded' manager pin under HedgeByDepth rolls descendants up to pinned × the cross-level hedge (pinned by test); infeasible pins land in the feasibility report with the unabsorbed amount (plus subtree_shortfall when protected descendants exceed the pin); is_pinned/pin_type mark provenance. Since v0.21.0 (issue #40) you don’t pass row_keys on batch outputs at all: cascade_many stamps the cascade identity on .attrs[’cascade_row_keys’] and apply_pins reads it — and if the keys are ever wrong (per-node columns poisoning the identity), it raises naming the offending columns instead of silently downgrading manager pins to leaf pins. And pin list order never matters (v0.22.0, issue #41): pins apply in canonical depth order internally — managers before leaves, stable within a depth — so the whole output frame, absorber rows included, is identical for any ordering, while the feasibility report keeps your list order. And a pin matching zero rows (v0.25.0, issue #48) no longer aborts the batch: apply_pins(..., on_missing='skip' or 'warn') drops it into the report (skipped=True, reason='node_absent'|'empty_scope') with no ghost side-effects — the node still absorbs and rescales normally; default stays 'error'. One recipe that falls out of all this (v0.22.1, issue #42): remainder pins. "These children are fixed, the unpinned one takes the rest" is just [Pin('T1', x), Pin('T2', y)] — pinned nodes never absorb for other pins, so the leftover lands on the unpinned siblings at baseline proportions with the parent conserved; add Pin(parent, total) to pin the envelope too.
